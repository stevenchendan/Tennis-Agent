# 严格 Review：HarshTomar1234/Tennis-Vision

> 审查对象：https://github.com/HarshTomar1234/Tennis-Vision（~2400 行 Python，单脚本管线）
> 审查方式：逐文件阅读源码（main.py / trackers / court_line_detector / mini_court / shot_classifier / requirements）。

## 一句话结论

这是一个**教程级脚本的化妆版**：代码结构明显源自广为流传的 tennis-analysis 教程
（YOLOv8 检测球员 + 自训练球检测模型 + ResNet50 14 点球场关键点 + mini court + pickle stub），
外面加了一层 "ENHANCEMENT" 注释。作为学习 CV 管线的材料合格；
作为"分析网球比赛"的产品基础不合格——而它最弱的部分（对击球的语义理解、
没有任何战术层）恰恰是你想做的方向最需要的。

## 硬伤（按严重程度）

### 1. 事件模型从根上就是错的：击球与落地不分

`ball_tracker.get_ball_shot_frames` 用"球的图像 y 方向反转 + 持续 25 帧"判定击球。
但**反弹（bounce）同样会让图像 y 反转**（球下落→弹起），bounce 和击球完全没有被区分：
反弹帧被当作击球、被计入"shot 数"、参与速度计算。整个统计层
（击球数、平均球速、回合）从数据源头上就是污染的。发球也检测不到
（序列第一段没有"之前的方向"可反转），所以 `ShotClassifier` 只能硬编码
"第一拍永远是发球"。

### 2. 击球分类是"表演"：正手/反手不可能从俯视 2D 位置推出来

`shot_classifier.py` 的判定逻辑：
- 正手/反手 = 球员站在哪半场 + 球往哪个方向飞。**俯视 2D 位置里根本没有
  正反手的信息**（那取决于球相对持拍手/身体的位置与握拍，需要姿态或至少
  球-身体侧向关系）。这个分类本质是掷硬币加包装。
- Volley = `abs(player_y - net_y) < 150`（像素！阈值随分辨率/迷你球场大小漂移）。
- Smash = 球的 y 位移超过迷你球场高度的 70% —— 底线对拉几乎每一拍都满足。
- 附带实锤 bug：图例取色 `get_shot_color("smash")`（小写）而字典键是
  `"Smash"`（大写），全部回落到默认白色，图例颜色从来没对过。

### 3. 速度是伪数字

- 球速 = 迷你球场平面距离 ÷ 相邻两次"击球"帧间时间 × 3.6。忽略弧线、
  忽略 bounce、忽略透视压缩，还把被误判为击球的反弹算进去。输出的
  "km/h" 有 misleading 的精确感。
- "average player speed" 用**对手的**击球数做分母，指标定义就是错的。

### 4. 工程质量

- `fps` 硬编码 24（`main.py` 里 `(end - start)/24`）；输入/输出路径、模型路径全部硬编码。
- 整段视频帧一次性读进内存（`read_video` 返回帧列表）；逐帧跑 YOLOv8x，CPU 上慢到不可用，
  没有批处理/抽帧/GPU 处理。
- 球场关键点模型只在**第 0 帧**推理一次——转播一旦切机位，后续全部帧的映射悄悄失效。
- pickle stub 按**固定路径**缓存：换视频后旧缓存被静默复用（还会读到别人/上次的数据）。
- `output_video_frames = video_frames.copy()` 是列表浅拷贝，注释却声称隔离。
- 无测试、无 CI、无类型标注、无配置系统、无 API/打包；`requirements.txt`
  不锁版本且注释里赫然写着 "Additional dependencies for cricket analysis"（从别的项目复制来的）。
- 仓库里提交了 569 行个人课程笔记（`notes/notes.py`）。
- README 声称 "advanced / high precision"，没有任何评测指标、没有量化验证。

### 5. 没有产品层（对你的目标最致命）

它的全部输出是一个画满涂鸦的 AVI：没有逐分切分、没有可查询的事件数据、
没有模式、没有解释、没有"所以呢"。**看不出任何可以学到并用于自己比赛的东西**。

## 值得肯定的部分

- 管线拆分（detection / court / mini-court / drawing）清晰可读；
- "stub 缓存检测结果避免重复推理"的思路正确（只是实现不安全）；
- 球场关键点 + 单应变换到标准球场的方向是对的；
- 画图工具函数中规中矩，能用。

## 对 Tennis-Agent 设计的直接影响

| Tennis-Vision 的问题 | Tennis-Agent 的对策 |
| --- | --- |
| bounce/击球混淆 | 事件在**球场坐标系**做：y 反转只可能来自击球（反弹不反转前进方向）；击球再用球员邻近确认；落地用"快→慢"速度台阶检测 |
| 发球漏检 | "球追踪空档后重新出现 + 持续移动"作为发球候选源 |
| FH/BH 伪分类 | 不做无法验证的声明；输出可验证的语义：方向（斜线/直线/中路）、深度区、deuce/ad 侧、是否截击（正确判据：击球前无落地） |
| 速度伪数字 | 明确标注为平面投影近似值，且只作为辅助信号 |
| fps/路径硬编码 | 全部走配置（`TENNIS_*` 环境变量），fps 从视频元数据读取 |
| 全量进内存 | 流式读帧（`iter_frames`） |
| 帧首关键点一锤定音 | 关键点模型可选；缺失时用球员/球分布拟合的代理映射并**明确降级标注** |
| 无战术层 | 模式挖掘器：发球方向有效性、发球+1、方向 n-gram、回合长度↔胜负、网前胜率，每张卡片带证据分号与可执行建议 |
| 无验证 | 24 个单元/E2E 测试，含"植入模式必须被找回"的端到端断言 |
| LLM 无用武之地 | LangChain 战术报告 + 教练问答，无 key 时降级为确定性模板 |
